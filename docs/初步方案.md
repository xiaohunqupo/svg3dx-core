# svg3dx 工具包开发方案

## 1. 总体架构

```
┌─────────────────────────────────────────────────────┐
│                  svg3dx-core (Rust)                  │
│  纯逻辑：XML解析 → 语义求值 → 几何指令序列生成       │
│  无几何内核依赖，无渲染依赖                          │
└──────────────┬──────────────────────┬───────────────┘
               │                      │
       ┌───────▼────────┐    ┌────────▼────────┐
       │  FFI: WASM     │    │  FFI: C ABI     │
       │  wasm-bindgen  │    │  extern "C"     │
       └───────┬────────┘    └────────┬────────┘
               │                      │
       ┌───────▼────────┐    ┌────────▼────────┐
       │  B端: three.js │    │  C端: VC++ 程序 │
       │  浏览器查看器  │    │  桌面客户端     │
       │  几何指令→渲染 │    │  几何指令→STEP  │
       └────────────────┘    └─────────────────┘
```

核心原则：**解析与求值只写一次（Rust），渲染与几何内核由各端自行选择。**

## 2. 核心 crate：`svg3dx-core`

### 2.1 职责

- 解析 svg3dx XML 文档，构建 DOM。
- 按命名空间识别 `s3dx:*` 元素，分派到语义求值器。
- 建立参数作用域，求值表达式，展开循环，求值条件。
- 处理布尔运算的顺序累积语义。
- 输出与渲染无关的**几何指令序列**（纯数据）。

### 2.2 不做什么

- 不做几何求值（不生成三角网格、不做实际布尔运算）。
- 不做渲染。
- 不绑定任何几何内核。
- 不处理相机、视口、投影。

### 2.3 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Rust | 一套代码编译到 WASM 和原生 DLL；内存安全；`serde` 生态适合几何指令序列化 |
| XML 解析 | `quick-xml` 或 `roxmltree` | 轻量、支持命名空间、纯 Rust、可编译到 WASM |
| 表达式求值 | 自写（基于 `nom` 或手写递归下降） | 语法子集小（`+ - * /`、比较、逻辑、括号、`[name]`、`var()`），无需完整表达式库 |
| 序列化 | `serde` + `serde_json`（或自定义二进制） | 几何指令序列在 FFI 边界传递需要序列化 |
| WASM 绑定 | `wasm-bindgen` + `serde-wasm-bindgen` | 标准方案，与 three.js 项目集成成熟 |
| C ABI 导出 | `extern "C"` + `#[no_mangle]` | VC++ 可直接链接 `.lib`，加载 `.dll` |
| 头文件生成 | `cbindgen` | 从 Rust 自动生成 C/C++ 头文件 |

### 2.5 几何指令序列的数据模型

这是 core 的输出，也是 FFI 边界的交换格式：

```rust
pub enum GeometryInstruction {
    Primitive {
        kind: PrimitiveKind,        // Box, Cylinder, Sphere, ...
        params: HashMap<String, Value>,
        transform: Mat4x3,          // 12 数三维变换
    },
    BoolOp {
        op: BoolOpKind,             // Union, Subtract, Intersect
        operands: Vec<GeometryInstruction>,
    },
    Instance {
        group_id: String,           // 引用 <g id="...">
        transform: Mat4x3,
    },
}
```

求值后的输出是一个 `Vec<GeometryInstruction>`，按文档顺序排列。B 端和 C 端各自消费这个序列，用自己的几何能力实现 `Primitive` 和 `BoolOp`。

**关键设计决策**：`BoolOp` 以树形结构保留，而不是在 core 里展平成最终网格。这样 C 端可以把它映射到 OCCT 的布尔运算，B 端可以映射到 three.js 的 CSG 库或 WASM 几何内核。core 不替它们做几何求值。

## 3. FFI 层

### 3.1 WASM 导出（B 端）

```rust
#[wasm_bindgen]
pub fn parse_svg3dx(input: &str) -> Result<JsValue, JsValue> {
    let doc = svg3dx_core::parse(input)?;
    let instructions = svg3dx_core::evaluate(doc)?;
    Ok(serde_wasm_bindgen::to_value(&instructions)?)
}
```

- 输入：SVG 文本（`&str`）。
- 输出：序列化为 JS 对象的几何指令序列，three.js 侧直接消费。
- 可选：暴露 `parse_with_external_params(input, params_js)` 支持外部参数注入。
- 构建：`wasm-pack build --target bundler`，Vite/Webpack 项目直接 `import`。

**Three.js 侧的消费方式**（B 端库的职责，不在 core 里）：

```js
import { parse_svg3dx } from 'svg3dx-core';

const instructions = parse_svg3dx(svgText);
const scene = new THREE.Scene();
for (const inst of instructions) {
  scene.add(buildThreeObject(inst));  // 你自己的映射逻辑
}
```

`buildThreeObject` 把 `Primitive` 映射为 `THREE.BoxGeometry`/`CylinderGeometry` 等，把 `BoolOp` 映射为 CSG 运算（如 `three-bvh-csg`）或交给 WASM 几何内核。

### 3.2 C ABI 导出（C 端）

```rust
#[no_mangle]
pub extern "C" fn svg3dx_parse(
    input: *const u8,
    input_len: usize,
) -> *mut Svg3dxResult {
    // 返回不透明指针，内部持有序列化后的指令序列
}

#[no_mangle]
pub extern "C" fn svg3dx_result_json(result: *const Svg3dxResult) -> *const u8 { ... }

#[no_mangle]
pub extern "C" fn svg3dx_result_len(result: *const Svg3dxResult) -> usize { ... }

#[no_mangle]
pub extern "C" fn svg3dx_free_result(result: *mut Svg3dxResult) { ... }
```

- 输入：UTF-8 字节缓冲区 + 长度。
- 输出：不透明指针，通过 `svg3dx_result_json` 取出 JSON 字节缓冲区，用完调 `svg3dx_free_result`。
- 内存管理：Rust 分配，Rust 释放。C++ 侧只持有指针，不负责 `delete`。
- 头文件：`cbindgen` 生成 `svg3dx.h`，VC++ 直接 `#include`。
- 构建：`cargo build --release`，产出 `svg3dx_core.dll` + `svg3dx_core.lib`。

**C 端的消费方式**（C 端程序的职责，不在 core 里）：

```cpp
#include "svg3dx.h"

auto* result = svg3dx_parse(data, len);
const uint8_t* json = svg3dx_result_json(result);
size_t json_len = svg3dx_result_len(result);
// 用 JSON 库解析指令序列，映射到 OCCT 的 BRepPrimAPI / BRepAlgoAPI
svg3dx_free_result(result);
```

## 4. B 端：three.js 库

### 4.1 包结构

```
svg3dx-three/
├── src/
│   ├── index.ts            # 入口，导出 Sv3dxViewer 类
│   ├── loader.ts           # 调用 WASM parse_svg3dx
│   ├── primitive.ts        # Primitive → THREE.Mesh/LineSegments
│   ├── bool.ts             # BoolOp → three-bvh-csg 或 WASM 内核
│   ├── model.ts            # s3dx:model 的 mode 切换（solid/wireframe/hidden-line）
│   └── transform.ts        # 12 数矩阵 → THREE.Matrix4
├── package.json
└── vite.config.ts
```

### 4.2 职责边界

- **不重新实现解析**：解析和求值全部委托给 `svg3dx-core` 的 WASM。
- **只做映射**：几何指令 → three.js 对象。
- **模型切换**：`solid`/`wireframe`/`hidden-line` 通过 three.js 的材质和渲染模式实现（`MeshStandardMaterial` / `MeshBasicMaterial({ wireframe: true })` / `EdgesGeometry`）。
- **布尔运算**：优先用 `three-bvh-csg`（纯 JS，轻量）；如果精度或性能不够，再接入 WASM 几何内核（如 Manifold 的 WASM 版本）。

### 4.3 依赖清单

| 依赖 | 用途 |
|---|---|
| `svg3dx-core`（WASM 包） | 解析 + 求值 |
| `three` | 渲染 |
| `three-bvh-csg`（可选） | 布尔运算 |
| Vite（开发时） | 构建、WASM 加载 |

## 5. C 端：桌面客户端

### 5.1 技术选型建议

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | C++（VC++） | 与 `svg3dx-core` 的 C ABI 直接对接；OCCT 是 C++ 生态 |
| GUI | Qt 或 Dear ImGui | Qt 成熟；ImGui 轻量，适合工具类客户端 |
| 解析 | `svg3dx-core.dll` | 复用 Rust 核心 |
| 几何内核 | Open CASCADE (OCCT) | B-rep 建模、布尔运算、STEP 导出 |
| STEP 导出 | OCCT 的 `STEPControl_Writer` | 标准方案 |
| JSON 解析 | `nlohmann/json` | 轻量、header-only |

### 5.2 流程

1. 读入 svg3dx 文件 → 字节缓冲区。
2. 调 `svg3dx_parse` → 拿到 JSON 格式的几何指令序列。
3. 用 `nlohmann/json` 解析指令序列。
4. 遍历指令：
   - `Primitive` → OCCT 的 `BRepPrimAPI_MakeBox` / `MakeCylinder` / `MakeSphere` 等。
   - `BoolOp` → OCCT 的 `BRepAlgoAPI_Fuse` / `Cut` / `Common`，按指令树的顺序递归求值。
   - `Instance` → 克隆已构建的 `TopoDS_Shape` 并应用变换。
5. 得到最终的 `TopoDS_Shape`。
6. 渲染预览（OCCT 的 `AIS_InteractiveContext` 或导出三角网格给 OpenGL）。
7. 导出：`STEPControl_Writer` 写 `.step` 文件；或 `BRepMesh` 三角化后导出 STL/glTF。

### 5.3 关于“依赖少”的说明

C 端如果只要“三角形和线”而不需要 STEP，可以不用 OCCT：把几何指令映射到简单的三角化逻辑（box → 12 个三角形，cylinder → 分段三角化），输出 glTF/STL，依赖只有 `svg3dx-core.dll` + 一个 JSON 库 + 一个轻量渲染库。

**STEP 导出是 OCCT 的职责，不是 core 的职责。** 这也是为什么 core 输出的是“几何指令树”而非最终网格——C 端可以选择用 OCCT 精确重建 B-rep，也可以选择轻量三角化。

## 6. 开发顺序

### 阶段一：core 解析与求值（无 FFI）

1. XML 解析 + 命名空间识别，构建 DOM。
2. 参数系统：作用域链、类型解析、表达式求值。
3. 循环展开（`loop-points`、`loop-range`）。
4. 条件求值（`if`/`ifnot`）。
5. `s3dx:exp` 属性覆盖。
6. 布尔元素顺序累积。
7. 几何指令序列生成。
8. 单元测试：用规范里的示例文件作为测试用例，验证指令序列的输出。

### 阶段二：WASM FFI + B 端最小可用

1. `wasm-bindgen` 导出 `parse_svg3dx`。
2. three.js 侧写 `buildThreeObject`，支持 `box`/`cylinder`/`sphere` 三种图元。
3. 用示例文件验证渲染。
4. 逐步补齐图元映射和布尔运算。

### 阶段三：C ABI FFI + C 端最小可用

1. `extern "C"` 导出 + `cbindgen` 生成头文件。
2. VC++ 侧写一个命令行工具：读文件 → 调 DLL → 打印指令序列 JSON。
3. 接入 OCCT：图元 → B-rep，布尔 → OCCT 布尔，导出 STEP。
4. 加 GUI（可选）。

### 阶段四：完善

1. 图元属性表逐项填充，core 和两端同步支持。
2. 错误处理：跳过+警告的完整实现。
3. 多模型切换（`active`、外部参数 `model=...`）。
4. 性能优化：大文件的流式解析、指令序列的二进制序列化（替代 JSON）。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| Rust 学习曲线 | core 逻辑不复杂（解析 + 求值），可参考 `quick-xml` 和 `nom` 的文档；FFI 层是薄封装 |
| WASM 体积 | `wasm-pack --release` + `wasm-opt`；core 不引入几何内核，体积可控 |
| 布尔运算在 B 端的精度/性能 | 先用 `three-bvh-csg` 验证；不够再换 Manifold WASM |
| OCCT 集成复杂度 | C 端先用命令行工具验证 STEP 导出链路，再加 GUI |
| 几何指令序列的 JSON 开销 | 初期用 JSON 便于调试；大文件场景再换二进制（`bincode`/`postcard`） |
| 规范与实现不同步 | 图元属性表以规范附录为准，core 的单元测试直接引用规范示例 |

## 9. 当前待定项对开发的影响

规范附录 10.1 的待定项中，对 core 开发有直接影响的是：

1. **图元属性表**：core 的 `primitives.rs` 需要每个图元的属性名、类型、默认值。建议先实现 `box`/`cylinder`/`sphere` 三个，其余按同一模式增量添加。
2. **`mode` 取值集**：B 端的 `model.ts` 需要知道支持哪些模式。先实现 `solid`/`wireframe`/`hidden-line`。
3. **`if` 与 `ifnot` 同时出现**：core 的 `condition.rs` 需要定一个行为（建议禁止，同时出现时报求值错误并跳过）。
4. **向量分量访问**：`[loop.value.x]` 是否支持，影响 `expr.rs` 的解析器设计。建议初版支持，因为实现成本低。

这些待定项不阻塞阶段一的开发——可以先按建议值实现，规范定稿时同步调整。
